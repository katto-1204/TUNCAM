# TUNCAM — Product Requirements Document

**Product name:** TUNCAM
**Parent project:** TunaEye (CNN-Based Computer Vision System for Automated Tuna Quality Assessment and Grading)
**Document owner:** TunaEye capstone team
**Status:** Draft v1.0

---

## 1. Overview

TUNCAM is a standalone data collection application built to support the TunaEye capstone project. It is used exclusively during dataset-building field sessions at fish landing centers (Bangkerohan, General Santos City) to capture standardized, labeled tuna sample images for training the MobileNetV3 grading model.

TUNCAM is **not** part of the deployed kiosk system. It is a separate tool used only by the research team and expert graders during data collection, before any model training happens.

## 2. Problem Statement

Manual data collection using a plain camera/phone introduces inconsistency: variable framing, inconsistent lighting exposure, no standardized crop region, and a disconnected labeling workflow (photos collected first, sorted and labeled later in folders/spreadsheets). This creates noise in the training dataset and increases risk of train/inference mismatch, since the kiosk's live capture pipeline expects a specific crop, color space, and framing that the training data must also reflect.

TUNCAM solves this by pairing image capture directly with an on-screen framing guide and immediate expert labeling, inside the same imaging chamber hardware (lightbox, top-mounted camera, LED strip lighting, fixed white sample platform) that will later be replicated in the kiosk.

## 3. Goals

- Standardize framing/positioning of every captured sample image
- Attach the correct grade label (or invalid/reject tag) to each image at the moment of capture, not after
- Reduce manual sorting and file-organization work for the research team
- Produce a dataset structure ready to feed directly into the training pipeline (crop → resize → color conversion → normalize → augmentation)
- Track source metadata (location, sample type) per image for later analysis

## 4. Non-Goals

- TUNCAM does not perform grading, inference, or run the MobileNetV3 model
- TUNCAM does not sync to any central server or dashboard
- TUNCAM is not deployed on the kiosk Raspberry Pi; it runs on a laptop/tablet used only during data collection trips

## 5. Target Users

- The capstone research team member operating the capture session
- The expert grader (e.g., Boss Jerry) assigning grade labels on-site, immediately after each capture

## 6. Hardware Context

TUNCAM is designed around the existing imaging chamber prototype:
- Enclosed lightbox with LED strip lighting (fixed, controlled illumination)
- Top-mounted webcam, fixed distance and angle
- White/foam sample platform, sample placed centered on platform
- Small object size relative to full frame (framing guide needed to ensure consistent centering and scale)

## 7. Functional Requirements

### 7.1 Live Camera Preview
- Real-time feed from the connected webcam displayed on screen
- Preview must reflect actual capture resolution/framing, not a cropped or scaled proxy

### 7.2 Framing/Positioning Guide (Overlay)
- Fixed rectangular or crosshair overlay on the live preview showing the exact region the sample should occupy
- Guide should approximate the crop region later used in the training pipeline, so raw captures are already close to the correct framing
- Optional: center-alignment indicator (e.g., color change or snap-guide) when sample is properly positioned

### 7.3 Pre-Capture Sample Type Selection
- Before the capture button is active, the operator must first select the sample type: **Sashibo Core** or **Tail-Cut**
- This selection determines which subfolder the resulting image is routed to; it must be set before each capture (or persist until changed for consecutive same-type samples)
- Capture is blocked/disabled until a sample type is selected, to prevent unlabeled captures

### 7.4 Capture
- Button/key trigger to snap and save the current frame at full resolution
- Filename format: `date-site-sampletypecode-grade-sequence`
- Sample type code: **Sashibo Core → `sc`**, **Tail-Cut → `tc`** (short code, not full label, keeps filenames compact)
- Grade is not yet known at the moment of capture — see 7.5, filename is finalized right after the grading modal is resolved
- Example final filename: `2026-08-17-bangkerohan-sc-A-001.jpg`, `2026-08-17-bangkerohan-tc-C-014.jpg`

### 7.5 Post-Capture Grading Modal
- Immediately after a successful capture, a modal/popup appears over the preview, blocking further action until resolved
- Modal presents four selectable options: **Grade A**, **Grade B**, **Grade C**, **Invalid**
- Grader taps one option; the modal closes, the grade code (`A`/`B`/`C`/`Invalid`) is inserted into the filename, and the image is instantly routed to its corresponding folder
- No image can remain unlabeled — the modal cannot be dismissed without a selection

### 7.6 Source Metadata Tagging
- Dropdown to select collection site before a session begins — **not limited to Bangkerohan**; the list should support adding any fish landing center or market as a selectable (and addable) entry, e.g., Bangkerohan, General Santos City, or any future site
- Metadata (site, date, sample type) attached to each saved image (embedded in filename and/or a companion metadata log)
- Note: folder names use the full sample type label (`Sashibo-Core`, `Tail-Cut`); only the filename itself uses the short code (`sc`, `tc`) to keep names compact

### 7.7 Date-Based Session Folders (Auto)
- Each data collection day is treated as its own session; a new top-level folder is auto-created (or selected) using the actual collection date
- Folder structure per session date:

```
/2026-08-17/               ← collection date
   /Sashibo-Core/
      /GradeA/
      /GradeB/
      /GradeC/
      /Invalid/
   /Tail-Cut/
      /GradeA/
      /GradeB/
      /GradeC/
      /Invalid/
/2026-08-24/                ← next collection day, same structure repeats
   /Sashibo-Core/
      ...
   /Tail-Cut/
      ...
```

- Every captured and labeled image is saved automatically into: `[Date]/[Sashibo-Core or Tail-Cut]/[GradeA|GradeB|GradeC|Invalid]/`
- No manual file-moving required after a session; date, sample type, and grade fully determine the save path

### 7.8 Session Log / Review
- Running counter per session showing images captured per grade and per sample type (helps track progress toward the 800+ per grade target)
- Simple gallery/list view to review and delete a bad capture before ending the session

### 7.9 Inter-Rater Support (optional, phase 2)
- Mode to re-open a batch of previously captured images for a second grader to independently label
- Log agreement/disagreement between first and second grader's labels for reliability checking

### 7.10 Keyboard/Hotkey Capture
- Spacebar or dedicated key triggers capture, number keys (1/2/3/4) select grade on the modal
- Speeds up the capture-to-label loop during long field sessions, reduces reliance on precise mouse/tap clicks

### 7.11 Local Progress Tracker
- Visual progress bar per grade class per sample type, showing count captured vs. the 800-image target
- Helps the team know at a glance which grade/type still needs more samples before ending a site visit

### 7.12 Session Metadata Export (CSV/JSON)
- At end of session, export a local manifest file listing every captured filename with its site, date, sample type, and grade
- Manifest saved locally alongside the image folders, useful for later dataset auditing without opening every folder

### 7.13 Low-Storage Warning
- App checks available local disk space and warns operator before storage runs out mid-session
- Prevents losing a capture or corrupting a save partway through a busy dock session

### 7.14 Quick Undo / Delete Last Capture
- One-tap "undo last capture" option immediately after a grading mistake, removes the file and rolls back the tally/counter
- Faster than digging into the review gallery for a capture made seconds ago

### 7.15 Camera Device Selector
- Dropdown to pick which connected camera to use, in case more than one webcam is plugged in or the primary one needs swapping mid-session
- Falls back gracefully with a clear message if no camera is detected

### 7.16 Idle/Sleep Prevention During Session
- Keeps the device screen and camera active while a collection session is running, preventing the OS from sleeping mid-capture
- Important for tablets/laptops with aggressive default power-saving settings

### 7.17 Operator/Grader Name Tag
- Simple field to record which team member ran the capture session and which expert grader assigned labels that day
- Attached to the session manifest, not required per-image, useful context for the inter-rater phase later

### 7.18 Local Backup Reminder
- End-of-session prompt reminding the operator to copy the day's folder to a backup drive/USB before leaving the site
- Purely a reminder, not automatic — no network transfer involved, keeps app fully offline

### 7.19 Storage Location Picker
- Operator can choose which local folder/drive the session data saves to at the start of a session (e.g., internal drive vs. external SSD)
- Useful when working across multiple field laptops or swapping storage media between sites

## 8. Non-Functional Requirements

- **Fully offline application** — no internet connection required at any point, not for startup, capture, labeling, storage, or session review. All processing and storage happen entirely on the local device
- No login, account, or cloud service dependency of any kind — app must launch and function on a device with no network access at all (landing centers frequently have zero signal/WiFi)
- Lightweight enough to run on a standard laptop or tablet, no special hardware beyond the webcam
- Fast capture-to-label loop (under a few seconds per sample) to keep pace with live grading sessions at the dock
- Stable under repeated use across a multi-hour collection session

## 9. Out of Scope / Future Considerations

- Auto-detection of sample boundaries (computer-vision-based auto-crop) — manual framing guide is sufficient for v1
- Reason/defect tagging (color rating, core condition, defect type) — noted as a possible future enhancement, not required for v1
- Cloud backup of collected images — local storage only for v1

## 10. Success Criteria

- 800+ correctly labeled, consistently framed images collected per grade class using TUNCAM
- Reduced post-collection sorting/labeling time compared to manual folder-based labeling
- Training dataset crop region matches kiosk inference crop region (verified by comparing a sample of TUNCAM captures against the training pipeline's expected input)
